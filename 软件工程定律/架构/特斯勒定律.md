## 什么是特斯勒定律

特斯勒定律认为，每个系统都有一部分不可避免的复杂度，你无法凭空消灭它，只能决定由谁来承担。软件工程里的很多设计选择，本质上都是在用户、业务方、调用方、平台层和开发者之间重新分配复杂度。所谓“更简单”的方案，通常只是把复杂度移到了别处。

## 核心要点

- 复杂度是守恒倾向，而不是想删就删。
- 好设计的关键不是零复杂度，而是让复杂度落在最能承受的一侧。
- 评估方案时，要问的是“复杂度转移给了谁、代价是什么”。

## 例子

### 例1：把兼容逻辑留给客户端，还是收敛到网关层
平台准备从 v1 API 迁移到 v2。方案一是要求所有客户端自己处理新旧字段差异，方案二是在网关层做协议适配。前者让平台实现简单，却把复杂度转嫁给几十个调用方；后者增加平台维护成本，但能统一控制兼容边界。这就是在决定复杂度落在哪里。

### 例2：订单状态机放在前端还是后端
如果前端自己拼装“待支付、支付中、已取消、退款中”等规则，页面开发会很灵活，但多个终端很快出现不一致。团队后来把状态机下沉到后端领域服务，由服务统一输出可展示状态，前端逻辑变简单，后端复杂度则上升。复杂度并未消失，只是被重新分配。

### 例3：数据库迁移是一次性脚本还是平台能力
小团队早期让开发者手工写 SQL 并在发布窗口执行，流程看似轻量，但回滚、审计和多环境一致性都压在个人经验上。随着服务增多，团队把迁移框架、版本管理和回滚策略建设成平台能力，虽然平台更复杂，却显著降低了业务团队的认知负担。

### 例4：可观测性是每个服务自建还是由平台统一提供
如果每个服务各自决定日志格式、指标名称和 Trace 采样策略，接入成本低，但排障时很难跨团队串联链路。统一接入标准会让平台和 SDK 更重，却能把排障复杂度从每个业务组手里收回来。工程实践中的难点，常常不是消除复杂度，而是选择谁来承担。

## 适用场景

适合用在平台化、协议设计、前后端边界划分、低代码系统和基础设施能力建设中。凡是有人说“把复杂度藏起来就好了”，都应该继续追问复杂度去了哪里。

## 常见误解

常见误解是把它解读成“优化没有意义”。实际上，复杂度转移本身就是优化的重要手段。关键是让承担复杂度的一方有更好的工具、专业能力和收益。

## 局限性与注意事项

不是所有复杂度都完全不可减。通过删除需求、减少变体和限制自由度，系统总复杂度确实可能下降。定律强调的是：剩余那部分核心复杂度总要有人承担。
