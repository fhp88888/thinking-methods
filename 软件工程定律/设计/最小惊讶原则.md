## 什么是最小惊讶原则

最小惊讶原则要求系统的命名、默认行为、错误反馈和交互方式尽量符合使用者的直觉预期。用户、调用方和维护者都在基于经验建立心理模型；当系统行为频繁违背这种模型时，即使技术上“说得通”，也会增加学习、排障和误用成本。

## 核心要点

- 一致、可预期的行为能显著降低认知负担。
- 让人惊讶的设计，会在使用和维护时持续制造摩擦。
- 所谓直觉，本质上来自既有约定、命名习惯和上下文一致性。

## 例子

### 例1：分页 API 的参数语义保持一致

一个内容平台的列表接口在大多数地方都使用 `page` 和 `pageSize`，但新建的搜索接口却改成了 `offset` 和 `limit`，而且 `page` 从 0 开始计数。结果前端复用原有分页组件时频繁拿错页码，测试同学也总要额外确认边界行为。遵循最小惊讶原则的做法，是让同类接口保持一致的参数命名、起始规则和返回结构，让调用方能把已有经验直接迁移过来。

### 例2：删除操作的默认行为不要偷偷扩大影响范围

后台管理系统里有一个“删除用户”按钮，产品预期只是停用账号，但后端实现却顺带删除了该用户的历史订单、评论和审计记录。运营人员第一次使用时并不知道会发生级联清理，结果造成数据恢复成本很高。更符合直觉的设计，是把默认操作做成“停用”或“软删除”，并把真正不可逆的级联删除明确标注、二次确认。

### 例3：重构后的模块仍然保留稳定入口

团队把原来的 `sendEmail(to, subject, body)` 重构成消息中心后，接口变成了需要先构造 `MessageBuilder`、再注入模板服务、最后调用异步派发器。虽然内部架构更灵活，但业务开发者只是想发一封普通通知邮件，却要理解更多概念，迁移时也很容易出错。更好的做法是保留一个简单直接的高频入口，把复杂扩展能力放在高级接口里，让常见用法仍符合旧有预期。

### 例4：表单交互遵循用户常见的 UX 习惯

一个 Web 表单把“保存”按钮放在左下角，把“取消”按钮放在高亮主按钮位置，并且按 Enter 键会直接提交到线上环境。新用户很容易因为肌肉记忆点错按钮，甚至在未检查内容前就触发正式提交。遵循最小惊讶原则时，按钮层级、颜色、位置和快捷键行为都应贴近用户熟悉的约定，减少不必要的认知切换。

## 适用场景

适合用在 API 设计、SDK 命名、UI 交互、配置默认值和错误提示设计中。每当系统行为与名字、文档或行业惯例不一致时，都应警惕会不会让人意外。

## 常见误解

常见误解是把“最小惊讶”理解成“永远不要创新”。原则并不反对新设计，只要求你在打破旧预期时，用命名、文档和反馈机制把新规则讲清楚。

## 局限性与注意事项

不同用户群的直觉并不完全相同，面向专家和面向大众的系统，合适的默认行为也可能不同。因此要结合目标用户，而不是抽象地追求所有人都不惊讶。
