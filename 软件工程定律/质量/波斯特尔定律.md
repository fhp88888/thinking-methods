## 什么是波斯特尔定律

波斯特尔定律原本用于网络协议设计，意思是发送方尽量遵守规范，接收方则尽量容忍合理范围内的差异。放到软件接口里，它提醒我们：自己输出的数据要稳定、严格、可预期；处理外部输入时则要对轻微差异有一定韧性，避免系统过于脆弱。

## 核心要点

- 对外输出越稳定，生态越容易围绕你形成可靠依赖。
- 对外部输入适度宽容，可以提升兼容性和抗抖动能力。
- 宽容不等于放任，边界必须可控且可观测。

## 例子

### 例1：接收端兼容多种时间格式
一个公共 API 曾同时面对老客户端和新客户端，于是服务端在解析时间字段时兼容时间戳、ISO 字符串和历史自定义格式，保证升级期间请求不至于全部失败。与此同时，服务端自己输出的时间格式始终保持一种明确规范，便于下游依赖。这就是“发送时保守，接收时宽容”的典型实践。

### 例2：过度宽容让坏数据悄悄入库
某用户资料服务为了“兼容前端各种输入”，把空字符串、非法手机号和拼错的国家码都默默接受，再由后台任务慢慢清洗。短期看调用方体验平滑，长期却让报表、通知和风控规则都建立在脏数据上。这个例子说明，宽容输入要有边界，否则就是把错误延后并扩大影响面。

### 例3：代码评审对接口契约做双向约束
团队在 review 中要求 SDK 对外发送的数据结构必须严格遵守文档，避免把未定义字段和模糊语义传播出去；但在消费第三方 webhook 时，会对字段顺序变化、可选字段缺失和大小写差异做有限兼容。这样既保护了自己的契约质量，也降低了外部不完美实现带来的脆弱性。关键是区分“我们应严格输出什么”与“我们应如何安全接收现实输入”。

### 例4：发布兼容策略减少升级事故
某平台废弃旧版本事件字段时，没有立即让接收端报错，而是先在网关层兼容新旧字段一段时间，同时在日志中标记旧格式调用来源。这样团队既保证了发布安全，也能基于观测数据推动调用方迁移。相比之下，如果既不兼容也不告警，就会在升级当天把所有问题一次性暴露给用户。

## 适用场景

适合用在 API 设计、消息协议、配置解析、数据导入和兼容性处理场景。特别是在多个团队或多个版本并行协作时，这条原则很有价值。

## 常见误解

常见误解是把“宽容接收”演变成无限制兜底，最后把脏数据一路吞进去。真正正确的做法是只对可预期、可解释的小偏差宽容，而不是对所有输入来者不拒。

## 局限性与注意事项

在安全、计费、合规等高风险场景，过度宽容可能放大风险。此时应当优先明确协议边界，把兼容性放在版本策略或迁移流程中处理。
