# THINKING METHODS 思维方式

这个仓库整理两类互补的知识：

- **通用思维方式**：拆解问题、组织判断、校验推理过程。
- **软件工程定律**：沉淀软件开发、架构设计、团队协作与技术决策中反复出现的规律。

前者偏通用认知工具，后者偏软件实践中的经验法则。各有侧重，所以按需来读就好。

## Quick intro

如果你是第一次打开这个仓库，可以这样使用：

- **遇到复杂问题，不知道从哪里下手**：先看[通用思维方式](#通用思维方式)
- **在做架构、团队、质量或规划决策**：先看[软件工程定律](#软件工程定律)
- **想快速建立整体地图**：先浏览下面两大类目录，再进入你关心的子类

## 通用思维方式

这部分是通用的一些思维方式，不仅仅局限于某个领域。

### 演绎推理

从一般到特殊，在前提成立时推出必然结论。

- [第一性原理](./通用思维方式/演绎推理/第一性原理.md)：回到最基本事实与约束，再从零推导方案。
- [三段论](./通用思维方式/演绎推理/三段论.md)：用“大前提 + 小前提”推出必然结论的经典推理形式。
- [公理化方法](./通用思维方式/演绎推理/公理化方法.md)：从少量基础公理出发构建完整理论体系。
- [反证法](./通用思维方式/演绎推理/反证法.md)：先假设结论不成立，再从矛盾中证明原命题为真。

### 归纳推理

从个别观察中总结规律，用有限样本形成一般判断。

- [枚举归纳](./通用思维方式/归纳推理/枚举归纳.md)：从多个个别案例中总结出一般规律。
- [统计归纳](./通用思维方式/归纳推理/统计归纳.md)：借助样本与概率，对总体作出有限置信度判断。
- [类比推理](./通用思维方式/归纳推理/类比推理.md)：根据两个对象的相似性推测它们在其他方面也可能相似。
- [模式识别](./通用思维方式/归纳推理/模式识别.md)：从杂乱现象中识别重复结构与潜在规律。

### 溯因推理

从结果反推最可能的原因，强调解释力与合理性。

- [最佳解释推理](./通用思维方式/溯因推理/最佳解释推理.md)：在多个可能原因中，选择解释力最强的那个。
- [假说演绎法](./通用思维方式/溯因推理/假说演绎法.md)：先提出假说，再通过推导与验证筛选解释。

### 批判性思维

审查论证、证据与假设，避免轻率接受结论。

- [逻辑谬误识别](./通用思维方式/批判性思维/逻辑谬误识别.md)：识别论证中常见的推理漏洞与说服陷阱。
- [质疑假设](./通用思维方式/批判性思维/质疑假设.md)：把默认前提拿出来检查，而不是直接接受。
- [证据评估](./通用思维方式/批判性思维/证据评估.md)：比较证据来源、质量与适用范围，再决定信任程度。

### 系统思维

把问题放进相互作用的整体中观察，而不是只盯局部。

- [反馈回路分析](./通用思维方式/系统思维/反馈回路分析.md)：观察系统中的强化回路与平衡回路如何影响结果。
- [涌现性思维](./通用思维方式/系统思维/涌现性思维.md)：理解整体行为如何从局部互动中自然出现。
- [全局/局部切换](./通用思维方式/系统思维/全局局部切换.md)：在局部细节与整体结构之间来回切换视角。

### 横向思维

跳出习惯路径，从不同角度寻找新解法。

- [逆向思维](./通用思维方式/横向思维/逆向思维.md)：从“怎样失败”或“反过来做”中发现新解法。
- [随机激发](./通用思维方式/横向思维/随机激发.md)：引入随机刺激，打破固有联想路径。
- [概念扇](./通用思维方式/横向思维/概念扇.md)：在抽象与具体之间展开概念空间，寻找替代方案。

### 模型思维

借助简化模型理解复杂现实，并提醒自己模型不是现实本身。

- [奥卡姆剃刀](./通用思维方式/模型思维/奥卡姆剃刀.md)：在多个解释里优先考虑假设更少的那个。
- [二八法则](./通用思维方式/模型思维/二八法则.md)：抓住少数高杠杆因素，往往能影响大部分结果。
- [地图非疆域](./通用思维方式/模型思维/地图非疆域.md)：记住模型只是现实的简化表示，不等于现实本身。
- [能力圈](./通用思维方式/模型思维/能力圈.md)：优先在自己真正理解的边界内判断和行动。

## 软件工程定律

这部分参考 [Laws of Software Engineering](https://lawsofsoftwareengineering.com/) 的分类与主要条目，在忠实原意的基础上做中文化重写，方便中文语境下快速查阅。

### 团队

关注组织结构、协作方式、知识分布与人员管理对软件交付的影响。

- [康威定律](./软件工程定律/团队/康威定律.md)：组织沟通结构往往会映射成系统结构。
- [布鲁克斯定律](./软件工程定律/团队/布鲁克斯定律.md)：给延期项目加人，常常会让项目更晚完成。
- [邓巴数](./软件工程定律/团队/邓巴数.md)：团队规模变大后，协作方式必须随之变化。
- [林格尔曼效应](./软件工程定律/团队/林格尔曼效应.md)：团队越大，个体平均投入和效率可能越低。
- [普赖斯定律](./软件工程定律/团队/普赖斯定律.md)：少数核心成员常常贡献了大部分关键产出。
- [普特定律](./软件工程定律/团队/普特定律.md)：技术与管理在组织里经常发生角色错配。
- [彼得原理](./软件工程定律/团队/彼得原理.md)：人容易被晋升到自己并不胜任的位置。
- [巴士因子](./软件工程定律/团队/巴士因子.md)：关键知识过度集中会让项目变得脆弱。
- [呆伯特原理](./软件工程定律/团队/呆伯特原理.md)：糟糕的组织可能把不适合产出的人推向管理岗位。

### 规划

关注估算、排期、目标设定与范围控制中的常见规律。

- [过早优化](./软件工程定律/规划/过早优化.md)：在确认瓶颈前做优化，往往只会先增加复杂度。
- [YAGNI](./软件工程定律/规划/YAGNI.md)：不要为假想需求提前建设功能或抽象。
- [帕金森定律](./软件工程定律/规划/帕金森定律.md)：工作会膨胀到填满你给它的时间。
- [九十九十定律](./软件工程定律/规划/九十九十定律.md)：软件最后那一点收尾，通常比想象中更费时。
- [霍夫施塔特定律](./软件工程定律/规划/霍夫施塔特定律.md)：任何事情都会比预期更久，即使你早就知道这一点。
- [古德哈特定律](./软件工程定律/规划/古德哈特定律.md)：指标一旦变成目标，就容易失去原本的衡量意义。
- [吉尔布定律](./软件工程定律/规划/吉尔布定律.md)：不完美的度量，通常也比完全没有度量更有用。

### 架构

关注接口契约、复杂度分布、分布式系统与架构演化。

- [海勒姆定律](./软件工程定律/架构/海勒姆定律.md)：只要用户足够多，任何可观察行为都可能被依赖。
- [高尔定律](./软件工程定律/架构/高尔定律.md)：复杂可用系统，通常是从简单可用系统演化而来。
- [抽象泄漏定律](./软件工程定律/架构/抽象泄漏定律.md)：抽象能隐藏复杂度，但在关键处总会露出底层细节。
- [特斯勒定律](./软件工程定律/架构/特斯勒定律.md)：复杂度不会消失，只会被转移到别处。
- [CAP定理](./软件工程定律/架构/CAP定理.md)：分区发生时，一致性与可用性必须做取舍。
- [第二系统效应](./软件工程定律/架构/第二系统效应.md)：第二代系统最容易因野心过大而失控。
- [分布式计算谬误](./软件工程定律/架构/分布式计算谬误.md)：很多分布式设计默认了一组并不成立的网络前提。
- [意外后果定律](./软件工程定律/架构/意外后果定律.md)：局部优化在复杂系统里常常会引发意料之外的副作用。
- [扎温斯基定律](./软件工程定律/架构/扎温斯基定律.md)：软件天然倾向于不断长出更多功能。

### 质量

关注代码质量、演化、测试策略与维护成本。

- [童子军原则](./软件工程定律/质量/童子军原则.md)：每次改动都顺手让代码比来时更干净一点。
- [墨菲定律](./软件工程定律/质量/墨菲定律.md)：任何可能出错的地方，最终都可能出错。
- [波斯特尔定律](./软件工程定律/质量/波斯特尔定律.md)：发送时保守，接收时宽容。
- [破窗理论](./软件工程定律/质量/破窗理论.md)：小问题长期不修，会让更多问题被默许和复制。
- [技术债](./软件工程定律/质量/技术债.md)：眼前省下的时间，常会在未来以更高成本偿还。
- [莱纳斯定律](./软件工程定律/质量/莱纳斯定律.md)：足够多的审视，通常能让问题更容易暴露。
- [柯尼汉定律](./软件工程定律/质量/柯尼汉定律.md)：写得太聪明的代码，往往也更难调试。
- [测试金字塔](./软件工程定律/质量/测试金字塔.md)：测试体系应重底层、轻昂贵脆弱的端到端测试。
- [杀虫剂悖论](./软件工程定律/质量/杀虫剂悖论.md)：重复同样的测试，发现新问题的能力会下降。
- [雷曼软件演化定律](./软件工程定律/质量/雷曼软件演化定律.md)：长期有价值的软件会持续变化，也会自然变复杂。
- [斯特金定律](./软件工程定律/质量/斯特金定律.md)：大多数东西其实都很平庸，筛选能力很重要。

### 规模

关注并行化、扩展性与网络效应。

- [阿姆达尔定律](./软件工程定律/规模/阿姆达尔定律.md)：整体加速效果受限于无法并行化的那一部分。
- [古斯塔夫森定律](./软件工程定律/规模/古斯塔夫森定律.md)：资源变多时，你也可以处理更大规模的问题。
- [梅特卡夫定律](./软件工程定律/规模/梅特卡夫定律.md)：网络类系统的价值会随连接数快速增长。

### 设计

关注简洁性、可维护性、耦合度与设计原则。

- [DRY原则](./软件工程定律/设计/DRY原则.md)：同一份知识不应在系统里被重复维护。
- [KISS原则](./软件工程定律/设计/KISS原则.md)：尽量用最简单直接的方式解决问题。
- [SOLID原则](./软件工程定律/设计/SOLID原则.md)：通过职责和依赖设计提升可维护性与扩展性。
- [迪米特法则](./软件工程定律/设计/迪米特法则.md)：对象应尽量少了解别人的内部细节。
- [最小惊讶原则](./软件工程定律/设计/最小惊讶原则.md)：系统行为应尽量符合人的直觉预期。
- [YAGNI](./软件工程定律/规划/YAGNI.md)：不要为未来假想场景预埋过多设计与实现。

### 决策

关注认知偏差、技术判断与战略取舍。

- [邓宁-克鲁格效应](./软件工程定律/决策/邓宁-克鲁格效应.md)：能力不足时，人更容易高估自己的判断。
- [汉隆剃刀](./软件工程定律/决策/汉隆剃刀.md)：能用疏忽解释的事，不必急着归因为恶意。
- [奥卡姆剃刀](./软件工程定律/决策/奥卡姆剃刀.md)：多个解释都成立时，优先考虑更简单的那个。
- [沉没成本谬误](./软件工程定律/决策/沉没成本谬误.md)：过去投入不该决定你是否继续错误方向。
- [地图不是疆域](./软件工程定律/决策/地图不是疆域.md)：模型和文档只是现实的抽象，不等于现实本身。
- [确认偏误](./软件工程定律/决策/确认偏误.md)：人会更容易接受支持自己原有判断的信息。
- [技术炒作周期与阿马拉定律](./软件工程定律/决策/技术炒作周期与阿马拉定律.md)：新技术常被高估短期影响、低估长期影响。
- [林迪效应](./软件工程定律/决策/林迪效应.md)：长期存活的非易腐事物，往往更可能继续存活。
- [第一性原理思维](./软件工程定律/决策/第一性原理思维.md)：回到最基础事实，再重新推导问题与方案。
- [反向思考](./软件工程定律/决策/反向思考.md)：先想怎样会失败，再反过来规避这些失败条件。
- [帕累托原则](./软件工程定律/决策/帕累托原则.md)：少数关键原因，常常决定大部分结果。
- [坎宁安定律](./软件工程定律/决策/坎宁安定律.md)：发布一个可纠正的草稿，往往比空白提问更快得到反馈。
